# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Projet

BrunoGUI_GenII : interface graphique d'échecs Windows (C# WinForms, .NET 8, `net8.0-windows`) qui pilote des moteurs UCI (Stockfish par défaut, plus Rodent IV, Sargon 1978, etc.). Licence GPL-3.0-or-later. Tout le code, les identifiants et les commentaires sont en français — garder cette convention.

## Commandes

```bash
dotnet build BrunoGUI_GenII.sln
```

```bash
dotnet run --project BrunoGUI_GenII.csproj
```

Tests de la logique d'échecs (projet console sans framework externe, `Tests/Program.cs`) :

```bash
dotnet run --project Tests
```

```bash
dotnet run --project Tests -- --complet
```

- Les tests couvrent les règles (roque, prise en passant, promotion, 50 coups, lecture FEN, conversion de variantes UCI), la notation PGN des coups ambigus (avec aller-retour écriture/relecture), la liste des coups (alignement, départ FEN, retour arrière, « # » du mat), le décodage des lignes UCI (`LigneUci`), la classe `Position` (copie, `CalculerSurCopie`), la classe `Partie` (qui est au trait, retour arrière, reprise après un mat, départ FEN, lecture seule, « Reprendre ici »), la classe `PiloteMoteur` avec un faux moteur `FauxMoteur` (bibliothèque puis moteur, analyse, abandon, coup UCI avec promotion), les évaluations et variantes du moteur (`Evaluation`, `SuiviAnalyse` : point de vue des Blancs, mat, score par variante, limite en coups entiers, promotion), la pendule (`Cadence`, `Pendule` avec un temps simulé, `PeutMater`) et des **perft** (chaque coup y est joué via `CalculerSurCopie`) comparés aux valeurs de référence (position initiale, Kiwipete, positions 3 à 5). `--complet` ajoute les perft profonds (~15 s). Toute modification du générateur de coups doit garder les perft verts.

- L'interface graphique n'a pas de tests : vérifier à la main dans l'application tout ce qui touche à `EchiquierPrincipal` ou au moteur.
- La solution compile sans avertissement : garder cet état.
- `CA1416` est désactivé dans le `.csproj`.
- `git` n'est pas dans le PATH de PowerShell sur cette machine : utiliser celui de Visual Studio 2022 (`C:\Program Files\Microsoft Visual Studio\2022\Community\Common7\IDE\CommonExtensions\Microsoft\TeamFoundation\Team Explorer\Git\cmd\git.exe`).
- GitHub Actions (`.github/workflows/tests.yml`) compile et lance les tests à chaque push. La compilation y passe `-p:SignManifests=false` : le certificat ClickOnce n'existe que sur le PC de développement.
- `.gitattributes` impose CRLF aux fichiers du projet (`.cs`, `.csproj`, `.sln`, `.resx`, `.md`, `.ini`, `.yml`) : écrire les nouveaux fichiers en CRLF.

## Architecture

**Point d'entrée** : `Program.cs` affiche le splash (`EcranDemarrage`), puis lance `EchiquierPrincipal` (palette par défaut de Krypton 95, pas de `KryptonManager`).

**`EchiquierPrincipal`** (~130 Ko) est le formulaire central : il gère l'échiquier, les menus, la feuille de partie, l'analyse et l'orchestration du moteur. Les autres formulaires (`ParametresDeBase`, `ParametresUciStockfish`, `PartieForceModule`, `AffichePgn`, `FichierPartiePgn`, `DonneesBrutesUci`, `FenetreAide`) sont des boîtes de dialogue secondaires.

**Classe `Position` + façade statique + événements statiques** — c'est le modèle clé à comprendre :
- `Position` (`Position.cs`) regroupe tout l'état d'une position : plateau 120 cases, trait, 4 droits de roque, case en passant, compteur des 50 coups, numéro de coup, `Echec`/`EchecetMat`. `Copier()` en fait une copie indépendante.
- `LogiqueMouvements.PositionActuelle` est la position de la partie. Les propriétés statiques historiques (`PiecesEchiquier`, `QuiJoue`, `PetitRoqueBlancPossible`…, `IndexCaseEnPassant`, `SansPrise`, `NombreCoupsJoues`, `Echec`, `EchecetMat`) ne sont que des raccourcis vers cet objet : le reste du code les utilise sans connaître `Position`. Tout nouvel élément d'état de la position doit être ajouté à `Position` (sinon il ne serait ni copié ni restauré).
- Restent hors de `Position` (état de partie ou de coup, non copié) : la liste des coups (`ListeCoups`), `CoupValide`. La pièce de promotion n'est pas un état : elle est passée à `ExecutionCoup(source, destination, promotion)` (moteur, bibliothèque, PGN, variantes, perft ; la couleur est toujours celle du pion, `PieceDeLaCouleur`, et `PieceDePromotion` lit une lettre UCI/PGN). Sans pièce fournie, `ExecutionCoup` demande à l'interface via `LogiqueMouvements.ChoixPromotion` (fonction `ColorPiece -> TypePiece`, branchée sur `EchiquierPrincipal.AffichePromotionPion`) ; sans interface ou sans choix : une dame. La fin de partie (mat, pat, nulle, abandon) n'est portée que par `Partie.Mode` (`Terminee`).
- `LogiqueMouvements` notifie l'UI via des événements statiques (`DessinePiece`, `DessineSymbole`, `AfficheCoupBlanc/Noir`, etc.) abonnés dans `EchiquierPrincipal.BrunoInterfaceGraphique_Load`.
- Les événements statiques sont invoqués avec `?.Invoke(...)` : la logique fonctionne sans interface abonnée (tests). Garder cette forme pour tout nouvel appel d'événement.
- `LogiqueMouvements.cs` n'a aucun `using` Windows Forms ni Krypton : la logique ne doit jamais afficher de fenêtre ni de message (utiliser un événement, une valeur de retour ou `Debug.WriteLine`).
- `EchiquierPrincipal._cheminMoteur` est toujours le chemin complet du moteur en cours, `_nomMoteurChoisi` son nom affiché. L'application ne change jamais son dossier courant (`MoteurUci.Start` fixe le dossier de travail du moteur).
- `MoteurUci` n'a aucun membre statique : l'objet `EchiquierPrincipal.MoteurUci` (gardé quand on change de moteur) est passé aux fenêtres de réglage (`ParametresDeBase`, `ParametresUciStockfish`). Il lance le moteur comme `Process` avec stdin/stdout redirigés. `ProcOutputDataReceived` s'exécute sur un **thread non-UI** : il décode chaque ligne une seule fois avec `LigneUci.Analyser` (résultat dans `MoteurUci.DerniereLigne`), puis déclenche `AfficheUci`, `AfficheDonneesBrutes`, `AfficheCoupMoteur` ; les gestionnaires côté formulaire doivent passer par `InvokeRequired`/`Invoke` et lire `DerniereLigne` plutôt que redécouper le texte. Les scores UCI sont du point de vue du camp au trait (mat négatif = le camp au trait est maté) ; ils sont convertis une fois pour toutes du point de vue des Blancs (camp au trait de `PositionDesVariantes`) par `AnalyseMoteur.cs` : tout ce qui est affiché suit la convention + = avantage blanc (« M3 » = les Blancs matent en 3).

**Evaluations et variantes** (`AnalyseMoteur.cs`, sans Windows Forms, testé) : `Evaluation` (centipions ou mat, du point de vue des Blancs ; `Texte`, `Symbole`, `Appreciation`, `TexteMat`), `LigneAnalyse` (numéro de variante, évaluation, `VariantePgn` limitée à `SuiviAnalyse.CoupsAffiches` coups **entiers**, `Debut`) et `SuiviAnalyse` (`_pilote.Lignes`, remis à zéro à chaque demande au moteur) qui garde la dernière ligne de **chaque** variante : une ligne sans score garde le score de sa propre variante. `AfficheInfoMoteur` ne fait qu'afficher ce que renvoie `_pilote.Lignes.Ajouter(ligne, PositionDesVariantes)`, et la fin d'analyse lit `_pilote.Lignes.Meilleure` : ne jamais relire un résultat dans le texte affiché d'un contrôle. Les réponses `bestmove (none)` / `0000` (aucun coup légal) sont traitées par l'interface dans `AfficheUci` : `LogiqueMouvements.CampAuTraitEnEchec()` distingue mat et pat. Le thread du moteur ne modifie jamais l'état de la partie.
- **Numérotation des demandes** (`SuiviDemandesMoteur.cs`, `MoteurUci.Demandes`) : chaque `go` reçoit un numéro, et le n-ième `bestmove` répond au n-ième `go` (garantie UCI). `MoteurUci.AbandonneDemandeEnCours()` envoie `stop` et rend la demande périmée : ses lignes `info` et son `bestmove` sont ignorés (`MoteurUci.LigneAbandonnee`, vérifié dans `AfficheUci` et `AfficheCoupMoteur` sur le thread de l'interface). `JeuMoteurUci` abandonne d'office la demande précédente. Côté interface, **toute action qui change la partie ou la position appelle `AbandonneReflexion()` en premier** (retour arrière, résultat, nouvelle partie, chargement, parcours, analyse, changement de moteur, coup de l'humain) : c'est ce qui permet de laisser les boutons actifs pendant la réflexion. Les lignes d'un ancien processus moteur sont ignorées (`sender != Proc`). Le nombre de variantes est centralisé dans `MoteurUci.NombreLignesPV` (initialisé depuis le `.ini`, modifié via `DefinitMultiPV`) : ne pas envoyer `MultiPV` en dur.
- Fenêtre du protocole (`DonneesBrutesUci.AjouteLigne`) : seules les 2 000 dernières lignes sont gardées (retaille par paquets de 500), et `EchiquierPrincipal.AfficheDonneesBrutes` prend le texte de la ligne tout de suite puis l'affiche par `BeginInvoke` (sans bloquer la lecture du moteur) : ne jamais relire `MoteurUci.DataUci` plus tard, la ligne suivante l'aura remplacé.
- **Joueurs affichés** : les noms et Elo des étiquettes et de l'en-tête PGN (`PartieEnCours.White/Black/WhiteElo/BlackElo`) ne s'écrivent que par `EchiquierPrincipal.AfficheJoueurs` (toujours ensemble ; une seule étiquette par camp, `LabelJoueurBlanc`/`LabelJoueurNoir`, au texte « [Elo] Nom » via `TexteJoueur`, « [?] Nom » si l'Elo est vide, rien sans nom ; ce sont des `EtiquetteUneLigne`, comme les pendules : un `Label` qui ne va jamais à la ligne, centré en hauteur, terminé par « … » si le texte est trop long ; les pendules ont `ReduitPourTenir` : leur police rétrécit jusqu'à ce que le temps tienne, ex : « 1:30:00 »). `AfficheJoueursDeLaPartie()` les déduit de `_partie.Blancs/Noirs` (`_nomHumain`/`_joueurElo` ou `_nomMoteur`/`_moteurElo`) : nouvelles parties, « Reprendre ici ». Après un chargement FEN, les noms sont vides (choix de Bruno : ce n'est la position ni de l'humain ni du moteur). `AfficheMoteurDansLaPartie` n'agit que si les noms affichés viennent de `AfficheJoueursDeLaPartie` (`_nomsHumainMoteur`) : après une FEN, une partie PGN, un en-tête saisi ou « humain contre humain », un changement de moteur ne touche pas aux noms. `AfficheMoteurDansLaPartie()` ne change que le ou les camps joués par le moteur (jamais un joueur humain ni une partie PGN chargée) : nom provisoire (nom du fichier) au changement de moteur, puis nom annoncé (`id name`), et Elo (`DefinitEloMoteur`, appelé par `ParametresDeBase`). La partie PGN chargée et la fenêtre « Entête PGN » passent leurs propres valeurs à `AfficheJoueurs`. Le temps de réflexion minimum est 1 s (`go movetime 0` ferait réfléchir Stockfish sans fin) : `LimiteTemps.Duree` l'impose.
- Réinitialiser une partie passe par `Outils.MiseaZeroListes()`.

**Calculs « pour voir »** : la légalité (`TestMouvementValide`), l'échec après un coup (`CoupNotationAlgebriquePGN`, qui met à jour `Echec` de la position réelle avec le résultat), le mat (`CalculeEchecEtMat`) et les variantes du moteur (`Outils.VarianteUciVersPgn`) s'exécutent dans `LogiqueMouvements.CalculerSurCopie(() => …)`. Cette fonction remplace temporairement `PositionActuelle` par une copie, puis remet l'originale, même en cas d'exception. Dans ce cadre, jouer les coups avec `SimuleCoup` (qui gère la tour du roque et le pion pris en passant, sans affichage), jamais `DeplacementPiece` seul. Tout ce qui est hors de `Position` (listes de coups, événements d'affichage) n'est **pas** protégé par la copie. Un calcul sur copie ne déclenche aucun redessin, contrairement à `MiseenplaceFen`.

**Position affichée ≠ position de la partie** : l'échiquier montre soit la partie (`PositionActuelle`), soit une position passée pendant le parcours (`EchiquierPrincipal._positionAffichee`, index `_indexAffiche` dans `ListeCoups`, -1 = position initiale). `AfficheCoupDeLaPartie(index)` (utilisé par Préc/Suiv/Début/Fin et par un clic sur la feuille de partie) lit la FEN avec `LogiqueMouvements.PositionDepuisFen` et la dessine sans toucher à la partie ; `RetourPositionCourante()` revient à la partie (bouton Fin, clic sur l'échiquier ou sur le dernier coup de la feuille). Retour arrière est grisé pendant le parcours (il annulerait un coup autre que celui affiché). Pendant le parcours, les cases restent cliquables (sauf partie en lecture seule), même quand ce n'est pas au joueur de jouer, pour que le clic ramène à la partie.

**Classe `Partie`** (`Partie.cs`, sans Windows Forms, testée) : `EchiquierPrincipal._partie` (exposée par `PartieCourante`) porte le mode de la partie (`ModePartie` : `AucunePartie`, `EnCours`, `Terminee`, `LectureSeule`), qui joue chaque camp (`Blancs`/`Noirs` : `Joueur.Humain` ou `Joueur.Moteur` ; `EntreHumains`, `JoueurAuTrait`, `MoteurAuTrait`, `HumainAuTrait`), `DepuisPosition` (départ FEN) et `RejeuPgn`. Ses actions : `Commencer(blancs, noirs)`, `CommencerDepuisPosition()` (l'humain joue le camp au trait), `Terminer()`, `Reprendre()`, `PasserEnLectureSeule()`, `MoteurPrendLeTrait()` (« Ordinateur joue »), `AnnulerDernierCoup()` (retour arrière : position rétablie depuis la FEN, reprise d'une partie terminée) et `ReprendreDepuis(index)` (bouton « Reprendre ici » du groupe de parcours, actif pendant le parcours et sur une partie PGN en lecture seule, y compris à sa position finale où rien n'est supprimé ; refusé sur un mat ou un pat : supprime les coups après la position affichée ; une partie terminée reprend, une partie PGN en lecture seule devient jouable avec l'humain au camp au trait ; le formulaire, `BoutonReprendreIci_Click`, efface le résultat, fixe les en-têtes et fait jouer le moteur si c'est son tour). Après un coup de l'humain, le moteur n'est sollicité que si `MoteurAuTrait` (donc jamais après un mat, un pat ou une nulle). Il n'existe plus de `_humain`, `_couleurHumain` ni `OrdinateurJoueBlanc/Noir` : tout passe par `_partie`.

**État de la partie et commandes actives** : `_partie.Mode` est le seul état de partie ; `MetAJourCommandes()` calcule **en un seul endroit** l'état de Retour arrière, Préc/Suiv/Début/Fin (et flèches du clavier), Analyse, Gain/Nulle, Ordinateur joue, Entête PGN, Saisie partie et du plateau (`MetAJourPlateau`, qui combine le mode, le parcours et `_plateauAutorise` = « c'est au joueur de bouger », fixé par `PlateauEnable`). Ne jamais écrire le `.Enabled` de ces commandes ailleurs : changer l'état puis appeler `MetAJourCommandes()`. Le mode change dans `CommencerPartie` (toutes les nouvelles parties → `EnCours`), `ChargementPartie.ChargerPosition` (`EnCours`), `ChargementPartie.ChargerPartiePgn` (`LectureSeule` à la fin), `GestionResultat` (`Terminee`, point de passage de toutes les fins : mat, pat, nulles, abandon) et `RetourArriere_Click` : un retour arrière sur une partie terminée la remet `EnCours` (`Partie.AnnulerDernierCoup`) et efface le résultat affiché (`EffaceResultat`). Pendant le parcours, les dessins demandés par la partie (coup du moteur) sont ignorés (`DessinePieceDeLaPartie`) et la partie continue normalement. `MiseenplaceFen` ne sert qu'aux actions qui **changent** la partie (retour arrière, chargement FEN) ; ces actions et les nouvelles parties appellent `QuitteParcours()` d'abord. L'analyse porte sur la position affichée (`_pilote.PositionAnalysee`) : ses variantes sont converties et numérotées sur cette position (`Outils.VarianteUciVersPgn(..., position)`, `LogiqueMouvements.DemiCoupAvant`, `EchiquierPrincipal.PositionDesVariantes`). Une partie PGN chargée est en lecture seule (`ModePartie.LectureSeule`) : sa position de partie est la position finale, et l'affichage démarre au début.

**Pilotage du moteur** (`PiloteMoteur.cs`, sans Windows Forms, testé avec un faux moteur) : `EchiquierPrincipal._pilote` mémorise ce qui est demandé au moteur (`Demande` : `TypeDemande.Aucune`, `CoupDePartie` ou `Analyse`, avec `PositionAnalysee`) et ne voit le moteur qu'à travers l'interface `IMoteur` (implémentée par `MoteurUci`). Le temps donné au moteur est une `LimiteTemps` (`Duree(ms)` → `go movetime`, `SansLimite` → `go infinite`, `ParPendule`/`DepuisPendule(pendule)` → `go wtime … btime … winc … binc …`, en millisecondes, jamais 0) : sa propriété `CommandeGo` (testée) est la commande envoyée par `MoteurUci.JeuMoteurUci`. `DemanderCoup(fen, limite)` essaie d'abord la bibliothèque (`ChoixBibliotheque`, fixé dans le constructeur du formulaire ; un coup de bibliothèque illégal laisse la main au moteur), `DemanderAnalyse(position, durée)` analyse une copie de la position, `Abandonner()` (appelé par `AbandonneReflexion`) renvoie `true` si le moteur réfléchissait, et `ReponseRecue()` (dans `AfficheCoupMoteur`, et pour `bestmove (none)`) dit à quelle demande répond un bestmove valable : un bestmove sans demande en cours est ignoré. `PiloteMoteur.JouerCoupUci("e7e8q")` joue un coup UCI, promotion comprise (coups du moteur et de la bibliothèque). Il n'existe plus de `_analyseEnCours` ni `_positionAnalysee` dans le formulaire ; l'affichage (minuterie, textes, couleurs, message de fin d'analyse) y reste.

**Pendule** (`Pendule.cs`, sans Windows Forms, testée) : `Cadence` (temps initial + bonus par coup, et pour une cadence à deux périodes `CoupsControle`/`TempsAjoute` : temps ajouté à chaque camp à son coup n° `CoupsControle` ; `Proposees` = Sans pendule, 3+2, 5+3, 10+5, 15+10, 30, `Fide` « 90 + 30 min (+30 s) FIDE » = 90 min pour 40 coups puis 30 min, 30 s par coup dès le début ; `Nom` affiché, `TimeControl` = balise PGN et valeur du `.ini` « 300+3 », « 40/5400+30:1800+30 » ou « - », relu par `Cadence.Lire`) et `Pendule` (seul le camp au trait décompte ; `Demarrer`, `CoupJoue(numeroDuCoup)` qui fige le temps, ajoute le bonus (et le temps de la 2e période au coup du contrôle) et passe à l'adversaire, refusé si le drapeau est tombé ; `Pause`/`Reprendre`, `Arreter`, `Restaurer` pour le retour arrière ; `TempsEcoule()` ; `Texte` pour l'affichage). L'heure vient d'une fonction (`Func<TimeSpan>` : un `Stopwatch` dans l'application, un temps simulé dans les tests) : la pendule calcule le temps écoulé au lieu de compter des tics. Temps écoulé = perte, sauf si l'adversaire ne peut pas mater (`LogiqueMouvements.PeutMater` : roi seul ou roi + une pièce légère = nulle, règle simplifiée des serveurs en ligne). Choix de Bruno : la cadence choisie vaut pour la partie suivante ; la pendule continue pendant le parcours, l'analyse la met en pause ; un moteur qui dépasse son temps perd.
- Côté formulaire (section « Pendule » d'`EchiquierPrincipal`) : `_cadence` = cadence choisie (liste `ListePendule` en bas, synchronisée avec `PartieForceModule.ChoixCadence` par `ChoisitCadence`, préférence `Cadence` du `.ini`) ; `_pendule` = pendule de la partie en cours, **null sans pendule** (comportement d'avant : temps fixe par coup). `NouvellePendule()` dans `CommencerPartie` et au chargement d'une FEN, `SupprimePendule()` au chargement d'une partie PGN, `Arreter()` dans `GestionResultat`. Après chaque coup, `CoupJoue` note les temps restants dans le `Coup` (`Pendule.NoteTemps` → `Coup.TempsBlancs/TempsNoirs`, null sans pendule) ; le retour arrière et « Reprendre ici » remettent la pendule à l'heure avec `Pendule.RestaurerDepuis(ListeCoups, QuiJoue)` (temps notés après le dernier coup restant ; aucun coup, ou coups sans temps : temps complets et pendule arrêtée jusqu'au prochain coup). Après un retour arrière où le moteur a le trait, la pendule est arrêtée (personne ne lui demande de jouer) et repart avec « Ordinateur joue ». « Reprendre ici » sur une partie PGN : nouvelle pendule de la cadence choisie. Balise PGN `[TimeControl]` (`PartieEchecsPGN.TimeControl`, fixée par `NouvellePendule`, écrite seulement avec une pendule, relue au chargement, modifiable dans la fenêtre « Entête PGN », champ « Cadence »). Temps après chaque coup : `RetourneContenuPgn(..., avecTemps: true)` écrit `{[%clk 0:02:51]}` (temps du camp qui vient de jouer, format Lichess/ChessBase) et reprend le numéro devant un coup noir qui suit un commentaire (« 1... e5 ») ; **seulement dans le fichier enregistré** (`EnregistrerPgn_Click`), jamais à l'affichage (choix de Bruno). À la lecture, `ParseurPgn.ExtraireCoups(pgn, garderTemps: true)` garde le `[%clk]` des commentaires de la partie principale (pas des variantes) sous la forme d'un mot `%clk=h:mm:ss`, que `DecodePartiePGN` range dans `PartieEchecsPGN.TempsCoups` (un élément par coup, null si inconnu) ; de même, le temps passé sur un coup `[%emt h:mm:ss]` (ChessBase) devient `%emt=` puis `PartieEchecsPGN.TempsReflexion` et `Coup.TempsReflexion`, affiché pendant le parcours sur la 1re ligne de variante (« (réflexion : 30 min 11 s) ») ; les sauts de ligne du commentaire sont retirés avant la recherche (ChessBase coupe « [%emt 0:⏎00:47] ») ; `ChargementPartie.ChargerPartiePgn` note dans chaque coup son temps et le dernier temps connu de l'autre camp (au départ : temps initial du `TimeControl`). Sans pendule en cours (partie PGN chargée), les pendules affichent ces temps à la position affichée (`TempsDeLaPositionAffichee`, appelé par `AffichePendules` après chaque déplacement du parcours). Les lignes de coups du PGN font au plus 80 caractères (on va à la ligne avant le coup qui dépasserait). Retour arrière : un demi-coup par clic (choix de Bruno, qui a écarté « le moteur rejoue », impossible à utiliser quand le moteur répond instantanément) ; si le moteur a alors le trait, l'échiquier attend et la ligne de variante 2 explique quoi faire. **Pause** : un clic sur l'une des pendules (`Pendule_Click`, curseur main) met la partie en pause (`_pauseJoueur` ; réflexion du moteur abandonnée, pendule en pause, pendules sur fond gris, échiquier bloqué par `MetAJourPlateau`), un autre clic la reprend (`FinPause`, et nouvelle demande au moteur s'il a le trait) ; la reprise automatique après une analyse ne s'applique pas pendant cette pause ; nouvelle partie, résultat, retour arrière, « Reprendre ici » et « Ordinateur joue » y mettent fin. La pendule ne démarre qu'au premier coup de la partie (`CoupJoue` : `Demarrer` si elle ne tourne pas encore), comme sur les serveurs. Le changement de camp se fait dans `CoupJoue` (point de passage de tous les coups de la partie : humain, moteur, bibliothèque), qui déclare la perte au temps si le coup arrive après la chute du drapeau. `JeuMoteurAvecBibliothèque` envoie `LimiteTemps.DepuisPendule(_pendule, numéro du coup à jouer)` (avec `movestogo` avant le contrôle d'une cadence à deux périodes) au lieu d'un temps fixe (pas de barre de réflexion `LancerReflexion` dans ce cas). `MinuteriePendule_Tick` (100 ms, heure lue sur `_chrono`, un `Stopwatch`) : reprise après une analyse (et nouvelle demande au moteur s'il devait jouer, l'analyse ayant interrompu sa réflexion), chute du drapeau → `PerteAuTemps` (sauf pendant le choix d'une promotion), affichage `AffichePendules` (`PenduleBlanc`/`PenduleNoir` à droite de l'étiquette de chaque camp, en haut du formulaire sans cadre autour ; toujours affichées, « -:-- » sans pendule ; fond vert pour le camp qui décompte, rouge sous 10 s). Le champ `TempsReflexionSecondes` (1 à 600 s, a remplacé le curseur) règle l'analyse et les coups du moteur sans pendule ; pendant une réflexion à temps fixe, la barre `BarreReflexion` se remplit (`LancerReflexion`, `Timer_Tick` toutes les 100 ms, `MiseaZéroTimer` la masque).

**Analyse de partie** (`AnalysePartie.cs`, sans Windows Forms, testée) : `AnalyseDePartie(ListeCoups)` construit les positions (départ, puis après chaque coup ; mat/pat jugés tout de suite, `ChancesFinDePartie`), donne la prochaine à analyser (`PositionSuivante`), reçoit la meilleure variante du moteur (`Enregistre(index, LigneAnalyse)` : évaluation du point de vue des Blancs et premier coup, `PremierCoup`), puis juge chaque coup (`Jugement(indexDansListeCoups)` → `JugementCoup` : camp, perte de chances, annotation proposée, évaluation après, meilleur coup, `MeilleurJoue` = perte nulle) et fait le bilan d'un camp (`Bilan` : imprécisions, erreurs, gaffes, perte moyenne en centipions). `JugementCoups` : chances de gain de -1 à +1 (formule de Lichess, ±1 pour un mat), seuils de Lichess sur la perte de chances : ?! dès 0,1, ? dès 0,2, ?? dès 0,3. Choix de Bruno : 3 s par position, toutes les parties, annotations proposées plus pâles que les siennes. Position sans score du moteur : sautée (`Ignoree`). `AppliqueAuxCoups` range les résultats dans les coups (`Coup.EvaluationApres`, `MeilleurCoup`, `MeilleurJoue`, et l'annotation proposée avec `Coup.AnnotationProposee`, jamais par-dessus une annotation du joueur ; le menu des annotations remet `AnnotationProposee` à false). Interface (section « Analyse de partie » d'`EchiquierPrincipal`, sous la feuille : `BoutonAnalysePartie` qui devient « Interrompre (k/N) », `BarreAnalysePartie`, `BilanAnalyse`) : chaque position est demandée par `_pilote.DemanderAnalyse` (`DureeAnalyseParPosition` = 3000 ms) et la réponse arrive dans `AfficheCoupMoteur` (ou `bestmove (none)` dans `AfficheUci`) → `PositionAnalyseeParLeMoteur` → position suivante ; pas de son ni de « Coup joué » pendant l'analyse ; échiquier bloqué (`MetAJourPlateau`), pendule en pause (pas de reprise dans `MinuteriePendule_Tick`) ; refusée pendant que le moteur réfléchit à son coup ; toute action qui change la partie l'interrompt (`AbandonneReflexion` → `TermineAnalyseDePartie(interrompue: true)`, ce qui est analysé est gardé) ; le parcours reste possible pendant l'analyse. Pendant le parcours, la 2e ligne de variante montre, centrée et en gras (`AfficheLigneAnalyse` ; `VarianteMoteurUci2_TextChanged` remet tout autre texte à gauche en police normale), « Analyse : -9.05 (-+)   joué Dh2 [?? Gaffe]   — meilleur : Rd3 (0.00) » (`TexteAnalyseDuCoup`) : l'évaluation après le coup, le coup joué et son annotation, puis le meilleur coup **avec son évaluation** (`Coup.EvaluationMeilleur`), et « écart négligeable » si la perte (`Coup.PerteAnalyse`) est sous le seuil d'imprécision : sinon un coup qui mate en 3 paraîtrait moins bon que le « meilleur » qui mate en 2. Pendant l'analyse, l'échiquier montre chaque position analysée (`AnalyseDePartie.IndexDansListeCoups` → `AfficheCoupDeLaPartie`), puis revient à la partie à la fin (`RetourPositionCourante`). Le bilan est effacé par `QuitteParcours` (nouvelle partie, chargement, « Reprendre ici »).

**Fins de partie** : mat et pat sont signalés par `ExecutionCoup` (événements `AfficheEchecEtMat` et `AffichePat`, qui donnent le camp maté ou pat ; `AfficheInfoEchec` ne fait qu'afficher un message).

**Couleurs** : un camp est toujours un `ColorPiece` (événements `AfficheTour`, `AfficheEchecEtMat`, `AffichePat`, `PartieForceModule.ChoixCouleur`, `Parametres.CouleurMoteur`), jamais une chaîne. Les textes affichés passent par `LogiqueMouvements.NomCouleur` (« Blanc », « le roi Blanc ») et `NomCamp` (« Blancs », « Trait aux Blancs ») ; `Adversaire(couleur)` donne l'autre camp. Le `.ini` garde `CouleurMoteur = Blancs/Noirs`. Les nulles automatiques passent par `LogiqueMouvements.RaisonNulle()` (triple répétition au sens FIDE avec la position initiale, 50 coups = 100 demi-coups, matériel insuffisant), appelée par l'interface après chaque coup ; elle renvoie `null` si le dernier coup a déjà maté ou pat (`DernierCoupTerminePartie`). Pendant le rejeu d'une partie PGN chargée (`Partie.RejeuPgn`), aucune nulle automatique n'est déclarée : le résultat du PGN fait foi.

**Droits de roque** : les 4 booléens `PetitRoqueBlancPossible`, `GrandRoqueBlancPossible`, `PetitRoqueNoirPossible`, `GrandRoqueNoirPossible` sont la seule source de vérité (lus/écrits dans la FEN, mis à jour dans `FaireMouvement`). `MiseenplaceFen` rétablit aussi la case en passant et le compteur des 50 coups : le retour arrière et la navigation dans la partie reposent dessus.

**Représentation de l'échiquier** : tableau « mailbox » de **120 cases** (10×12). a1 = index 21, h8 = index 98 ; les cases hors plateau valent `TypePiece.Bordure`. Les `PictureBox` de l'UI (dans `VueEchiquier`) sont indexées de la même façon. Voir le schéma en tête de `LogiqueMouvements.cs`. Dans `TypePiece`, les pièces noires ont des valeurs paires et les blanches impaires.

**Liste des coups** (`Coup.cs`) : `LogiqueMouvements.ListeCoups` est une liste d'objets `Coup` qui portent toutes les notations d'un coup (FEN de la position **après** le coup, PGN international, PGN français R/D/T/F/C, NAL, UCI ; le numéro « 12. » n'est écrit que devant les coups blancs, puis « # », « + » ou rien, puis un espace). `ListeCoupsFen`, `ListeCoupsPgnIntl`, `ListeCoupsPgnFr`, `ListeCoupsNal`, `ListeCoupsUci` sont des **vues en lecture seule** (`VueCoups`) de cette liste, toujours alignées : on ne la modifie que par `AjouteCoup`, `AjoutePositionDeDepart`, `RetireDernierCoup` (qui ne retire jamais la position de départ) et `ViderCoups`. Une partie chargée depuis un FEN commence par un élément `Coup.PositionDeDepart` (notations vides) : le code qui parcourt les coups joués doit l'ignorer (`EstPositionDeDepart`). Le « # » du mat est posé par `ExecutionCoup`, qui ne positionne toutefois `EchecetMat` qu'après les événements `AfficheCoupBlanc`/`AfficheCoupNoir` (l'interface en dépend).

**Autres modules** :
- `Bibliotheque.cs` : lecture des livres d'ouvertures Polyglot `.bin` (calcul de clé Zobrist, table Random64, lecture big-endian) et choix du coup (`ChoisirEntree` : meilleur poids, au hasard parmi les ex aequo, ou n'importe lequel en mode aléatoire ; testé). Côté formulaire, `AfficheCoupsBibliotheque(fen)` affiche seulement la liste des coups connus ; `ChoisirCoupBibliotheque(fen)` (le `ChoixBibliotheque` du pilote) choisit le coup que le moteur joue et le marque ⭐.
- `GestionPartiePgn.cs` / `FichierPartiePgn.cs` : génération/sauvegarde PGN (lignes ≤ 80 caractères ; balises `[SetUp "1"]`/`[FEN]` pour une partie commencée à une position, « n... » devant un premier coup noir, résultat `*` pour une partie en cours), en-têtes (`SaisieBalises`, qui ne modifie la partie qu'à l'enregistrement), et parseur PGN (`ParseurPgn.ExtraireCoups` : variantes imbriquées comptées en profondeur, commentaires `{}` et `;`). `DecodeCoupPartie(coup)` joue un coup SAN pour le **camp au trait de la position** (roque `0-0` accepté) et renvoie `false` sans rien jouer ni lever d'exception si le coup est illisible ou illégal.
- `ChargementPartie.cs` (sans Windows Forms, testé) : `ChargerPosition(fen, partie)` (FEN contrôlée par `ErreurFen`, qui renvoie la raison du refus ou `null` : 6 champs, 8 rangées de 8 cases, un roi par camp, pas de pion sur les rangées 1 et 8, trait, roques, en passant, compteurs, camp sans le trait pas en échec ; une FEN n'est jamais lue sans ce contrôle, `LitFen` planterait ; `NormaliseFen` met un seul espace entre les champs ; l'humain joue le camp au trait). Un fichier FEN de plusieurs lignes : la première position est chargée (`ChargePositionFen_Click`) et `ChargerPartiePgn(pgn, partie)`, qui rejoue la partie (depuis sa balise `FEN` s'il y en a une : élément `Coup.PositionDeDepart`, `Partie.Commencer(..., depuisPosition: true)`), s'arrête au premier coup illisible ou illégal, met la partie en lecture seule et renvoie un `ResultatChargementPgn` (FEN incomplète, coup illisible, demi-coups joués). Le formulaire (`ChargePositionFen_Click`, `ChargerPartieDepuisPgn`) n'y ajoute que les dialogues, les messages et les textes affichés.
- Lecture des fichiers PGN : `FichierPartiePgn.LireTextePgn` (`DecodeLignes`) lit chaque **ligne** en UTF-8 strict, ou en Latin-1 si elle n'en est pas, et retire toutes les marques UTF-8 (BOM) : un fichier aux encodages mélangés (cas réel : `BrunoAllGames.pgn`, 4 lignes Latin-1 sur 14 819) relu en entier en Latin-1 abîmait tous les accents et faisait de la marque du début un faux 1er coup « ï»¿ ». Des parties réelles annotées (Fritz, ChessBase) sont dans `Tests\PartiesAnnotees.pgn`, copié à côté des tests ; le nettoyage des « .. » de « 12... » ne touche que les lignes de coups, jamais les en-têtes (les annotations `!`, `?` sont gardées).
- **Affichage de l'échiquier** (`VueEchiquier.cs`, `EchiquierPrincipal._vue`) : les 120 cases `PictureBox` (64 visibles, indexées comme le tableau mailbox), les images des pièces et des symboles, les couleurs des cases (`ChangeCouleurs`, lues/enregistrées dans les préférences via `_vue.CaseClaire/CaseSombre/CaseSource/CaseDestination`), les cases colorées du dernier coup du moteur (`MontreDernierCoup`, `EffaceDernierCoup`, `DernierCoupMasque` = true pendant le parcours), l'inversion (`Tourner`, `CoteNoir`, `IndexDeLaCase` pour un clic), l'activation des cases (`ActiverCases`, appelé seulement par `MetAJourPlateau`) et le curseur « pièce » (`MetCurseurPiece`/`LibereCurseurPiece`, icône libérée). Toute image de case passe par `RemplaceImage`, qui libère les images composées pièce + symbole. La vue ne connaît ni les règles ni la partie : le formulaire décide quoi montrer. Ne plus manipuler de `PictureBox` de case dans le formulaire. Pendant le choix d'une promotion (`AffichePromotionPion`), tous les autres contrôles et le clavier sont inactifs, puis rétablis.
- **Feuille de partie** (`FeuilleCoups.cs`, `EchiquierPrincipal.FeuilleDesCoups`, à droite de l'échiquier ; a remplacé la fenêtre « Liste des coups ») : composant dessiné à la main (`ScrollableControl`), une ligne « n° | blanc | noir » par coup complet, coup de la position affichée surligné, survol, défilement automatique jusqu'au coup surligné ; événements `CoupClique` (→ `AfficheCoupDeLaPartie`) et `CoupCliqueDroit`. La mise en page vient de `FeuilleDePartie.Lignes` (`Coup.cs`, testée : `LigneFeuille(Numero, Blanc, Noir)` = place des coups dans `ListeCoups`, null pour une case vide, ex : « 3. | ... | Cf6 » d'une partie commencée par un coup noir). `MetAJourFeuille()` est appelée par `MetAJourCommandes()` : la feuille suit donc la partie et le parcours sans autre appel. **Annotations** (`Coup.Annotation` : « !! », « ! », « !? », « ?! », « ? », « ?? » ou vide ; classe `Annotations` dans `Coup.cs`, testée : `Toutes`, `Nom`, `DepuisNag` pour les codes $1 à $6, `Separe` pour « Ng5?! ») : clic droit sur un coup de la feuille (`FeuilleDesCoups_CoupCliqueDroit`, menu avec l'annotation actuelle cochée), symbole dessiné en couleur après le coup (`FeuilleCoups.CouleurAnnotation`), écrit collé au coup dans le PGN (`RetourneContenuPgn`, affichage comme fichier), relu au chargement : les `!` et `?` ne sont plus effacés des lignes de coups par `DecodeFichierPGN`, `DecodePartiePGN` les sépare du coup et lit aussi les codes $1 à $6 de la partie principale (`PartieEchecsPGN.Annotations`, une par coup), et `ChargerPartiePgn` les range dans les coups.
- `Bibliotheque.cs` : une bibliothèque introuvable lève une exception claire au chargement (`PolyglotBibliothèqueLecture`, la précédente reste active) et `TrouverLesEntrées` ne renvoie alors aucun coup (`PolyglotBibliothèque.Disponible`) ; `EchiquierPrincipal.RécupèreBibliothèque` affiche un message au lieu de planter.
- Fenêtres secondaires : la liste des parties PGN (`FichierPartiePgn`), comme les autres, est masquée par la croix rouge et jamais détruite ; le texte du bouton « Affiche/Masque liste parties » suit sa visibilité. Les nouvelles parties (menus, dialogue Stockfish) et l'ouverture d'un fichier PGN ne changent rien avant la confirmation : « Annuler » laisse la partie et la réflexion du moteur intactes.
- `MiseAJourStockfish.cs` : deux étapes. `RechercherNouvelleVersion` compare `sf_<n>` (tiré de `id name Stockfish <n>`) au tag de la dernière release GitHub et renvoie la version (tag, lien, taille) ou `null` si à jour, sans rien arrêter ni télécharger. `Installer` télécharge le zip Windows adapté (`ChoisirArchive`, testé : depuis Stockfish 19, un seul binaire « universal » par processeur, `x86-64` ou `arm64` selon `RuntimeInformation.OSArchitecture`) et remplace le `stockfish.exe` **du dossier de sortie** (arrêt des seuls processus lancés depuis ce fichier, après le téléchargement ; sauvegarde `.old` restaurée si la nouvelle version ne répond pas `uciok` ; quelques nouvelles tentatives si le fichier est verrouillé, ex : par OneDrive). Le moteur doit ensuite être redémarré. Attention : une recompilation complète (Rebuild, `--no-incremental`) nettoie le dossier de sortie et y recopie le `stockfish\stockfish.exe` du dépôt (version plus ancienne) : il faut alors refaire la mise à jour. Au démarrage (`EchiquierPrincipal.VerificationAutomatiqueMiseAJour`, avant `MoteurUci.Start`), la recherche n'a lieu que tous les `VerificationMiseAJourJours` jours (`BrunoGUI.ini`, 30 par défaut, 0 = jamais ; date `DerniereVerificationMiseAJour` dans les préférences) ; au démarrage comme par le bouton, l'installation n'a lieu qu'après accord de l'utilisateur (`DemandeInstallation`). Une exception signale une vraie erreur (ex : hors ligne). Le `.csproj` copie `stockfish\stockfish.exe` en `PreserveNewest` pour ne pas écraser une version mise à jour à chaque compilation.

## Chemins et fichiers d'exécution

- `Chemins.RepertoireRacine` = `Application.StartupPath` (déploiement portable) : moteurs, livres et `.ini` sont cherchés **à côté de l'exécutable**, pas à la racine du dépôt. Un fichier ajouté dans `Moteurs_UCI\` ou `BibliothèquesPolyglot\` doit donc être déclaré dans le `.csproj` avec `CopyToOutputDirectory` (seuls Rodent IV, Sargon et `stockfish\stockfish.exe` le sont côté moteurs).
- `BrunoGUI.ini` (format `clé = valeur`, `;` pour les commentaires) est lu par `Parametres.ChargerDepuisIni`. Seules les clés présentes dans le `switch` sont lues ; une nouvelle clé doit y être ajoutée. Les couleurs acceptent un nom .NET (`Peru`) ou un code `#RRGGBB` (`Parametres.ConvertitCouleur`), avec le style Lichess par défaut. `NombreCoeursThread` et `TableHachage` sont envoyés au moteur à la réception de `uciok` (`MoteurUci.EnvoieOptionsDemarrage`), une seule fois, seulement si le moteur déclare ces options et **seulement à Stockfish** (`MoteurUci.NomAnnonce`) : avec plusieurs threads, Rodent IV ignore MultiPV. **Deux fichiers** : `BrunoGUI.ini` contient les valeurs par défaut, livrées avec l'application et **jamais écrites** par elle (copié en `Always` : on peut le modifier librement dans le dépôt). `BrunoGUI.preferences.ini`, créé à côté de l'exécutable (hors dépôt), contient les préférences personnelles : `Parametres.Charger(dossier)` lit le premier puis le second par-dessus. À la fermeture, `EchiquierPrincipal.SauvePreferences` y enregistre les réglages de l'interface (couleurs, nom, temps de réflexion, choix de « Nouvelle partie », MultiPV, Threads, Hash, bibliothèque) via `Parametres.SauverPreferences`, qui remplace les valeurs sur place en conservant commentaires, ordre et clés inconnues. Le moteur, son site, l'Elo de l'humain et la palette restent uniquement dans `BrunoGUI.ini`. La clé `Palette` (nom d'un `Krypton.Toolkit.PaletteMode`, ex : `Microsoft365Silver`, `Office2013White`) choisit la palette de toute l'application (`Program.ConfigureKrypton`, qui met aussi les boutons des boîtes de message en français) ; absente : `Microsoft365Blue`, la palette par défaut de Krypton 95. Les réglages Threads/Hash passent par `MoteurUci.DefinitThreads`/`DefinitHachage` (mémorisés et renvoyés à chaque redémarrage du moteur, par exemple à chaque « Nouvelle partie »).
- `BrunoGUI.ini`, `Bruno_NB.jpg` et `AideBrunoGUI.rtf` sont cherchés via `Chemins.RepertoireRacine` : ne jamais utiliser de chemin relatif au dossier courant (l'application est parfois lancée depuis un raccourci).
- Le dossier `Tests\` est exclu de la compilation de l'application dans `BrunoGUI_GenII.csproj` (le projet racine inclut sinon tous les `.cs` des sous-dossiers).
- `stockfish\src\` et `stockfish\wiki\` sont les sources/doc upstream de Stockfish, fournies pour référence — elles ne font pas partie du build C#.
