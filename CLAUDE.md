# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Projet

BrunoGUI_GenII : interface graphique d'échecs Windows (C# WinForms, .NET 10, `net10.0-windows` depuis le 2026-10-27 : fin du support de .NET 8 le 2026-11-10 ; il faut Visual Studio 2026, VS 2022 ne prend pas .NET 10 en charge) qui pilote des moteurs UCI (Stockfish par défaut, plus Rodent IV, Sargon 1978, etc.). Licence GPL-3.0-or-later. Tout le code, les identifiants et les commentaires sont en français — garder cette convention. Les **identifiants n'ont pas d'accents** (`RecupereBibliotheque`, `PolyglotBibliotheque` ; renommés le 2026-10-09), les commentaires et les textes affichés en ont ; seules exceptions : les noms de ressources générés (`Bouton_arrêt_48pixel`…) et le dossier `BibliothèquesPolyglot` sur le disque (propriété `Chemins.BibliothequesPolyglot`).

## Architecture

**Point d'entrée** : `Program.cs` affiche le splash (`EcranDemarrage`), puis lance `EchiquierPrincipal` (palette par défaut de Krypton 95, pas de `KryptonManager`).

**`EchiquierPrincipal`** est le formulaire central : il gère l'échiquier, les menus, la feuille de partie, l'analyse et l'orchestration du moteur. Il est découpé en **fichiers partiels par sujet** (rangés sous `EchiquierPrincipal.cs` dans Visual Studio, `DependentUpon` + `SubType Code` dans le `.csproj`) : `EchiquierPrincipal.cs` (initialisation, clics sur l'échiquier, menus, boutons, résultats, état des commandes `MetAJourCommandes`, feuille), `.Moteur.cs` (réponses UCI, coup du moteur, bibliothèque, réflexion à temps fixe, `AbandonneReflexion`), `.Pendule.cs`, `.Parcours.cs` (boutons et clavier du parcours, position affichée, analyse du coup regardé, flèches, lignes de variantes), `.Fichiers.cs` (PGN, FEN, saisie de position, chargement d'une partie PGN), `.AnalysePartie.cs`. Un nouveau sujet va dans son fichier ; un nouveau fichier partiel est à déclarer dans le `.csproj`.

**Version** : la balise `<Version>` du `.csproj` (ex : 1.16) est LE numéro de version : assembly et propriétés de l'exe, « A propos » (`EchiquierPrincipal.VersionAffichee`, mineur sur deux chiffres). Pour publier : changer `<Version>`, ajouter la ligne d'historique dans `Apropos_Click`, pousser, puis le tag `vX.YY` ; le workflow de publication refuse un tag qui ne correspond pas à `<Version>`. Les autres formulaires (`ParametresDeBase`, `ParametresUciStockfish`, `PartieForceModule`, `AffichePgn`, `FichierPartiePgn`, `DonneesBrutesUci`) sont des boîtes de dialogue secondaires. **Aide** : pages HTML `Aide\fr\index.html` et `Aide\en\index.html` (style commun `Aide\aide.css`, captures dans `Aide\<langue>\images`, la page anglaise reprend les images françaises qui lui manquent), copiées à côté de l'exe et ouvertes dans le navigateur par le menu Aide / Documentation (`AideDocumentation_Click`, page de `Langue.Code`) ; toute nouvelle fonction visible doit y être décrite, dans les deux langues.

**Classe `Position` + façade statique + événements statiques** — c'est le modèle clé à comprendre :
- `Position` (`Position.cs`) regroupe tout l'état d'une position : plateau 120 cases, trait, 4 droits de roque, case en passant, compteur des 50 coups, numéro de coup, `Echec`/`EchecetMat`. `Copier()` en fait une copie indépendante.
- `LogiqueMouvements.PositionActuelle` est la position de la partie. Les propriétés statiques historiques (`PiecesEchiquier`, `QuiJoue`, `PetitRoqueBlancPossible`…, `IndexCaseEnPassant`, `SansPrise`, `NombreCoupsJoues`, `Echec`, `EchecetMat`) ne sont que des raccourcis vers cet objet : le reste du code les utilise sans connaître `Position`. Tout nouvel élément d'état de la position doit être ajouté à `Position` (sinon il ne serait ni copié ni restauré).
- Restent hors de `Position` (état de partie ou de coup, non copié) : la liste des coups (`ListeCoups`), `CoupValide`. La pièce de promotion n'est pas un état : elle est passée à `ExecutionCoup(source, destination, promotion)` (moteur, bibliothèque, PGN, variantes, perft ; la couleur est toujours celle du pion, `PieceDeLaCouleur`, et `PieceDePromotion` lit une lettre UCI/PGN). Sans pièce fournie, `ExecutionCoup` demande à l'interface via `LogiqueMouvements.ChoixPromotion` (fonction `ColorPiece -> TypePiece`, branchée sur `EchiquierPrincipal.AffichePromotionPion`) ; sans interface ou sans choix : une dame. La fin de partie (mat, pat, nulle, abandon) n'est portée que par `Partie.Mode` (`Terminee`).
- **Les règles** sont dans `Regles.cs` (classe statique sans aucun état ni affichage, depuis le 2026-10-23, étape 1 du chantier « état partagé ») : chaque fonction reçoit la `Position` sur laquelle elle travaille et ne lit jamais `PositionActuelle` : `LireFen`/`LireFenDans`/`Fen`, `Mouvements` (pseudo-légaux, « e4 »/« xe5 »), `EstLegal`, `MouvementsValides`, `CoupsLegaux`, `ResteCoupsJouables`, `RoiAttaque`, `CampAuTraitEnEchec`, `EstMat`, `CasesPiecesMenacantes`, `SimuleCoup`, `Jouer` (le coup complet : roques, en passant, 50 coups, trait, numéro ; promotion fournie, Vide = dame ; renvoie un `ResultatCoup`), `EstPromotion`, `Notation` (française, sans +/#, et l'échec qui suit), `MaterielInsuffisant`, `PeutMater`. `LogiqueMouvements` n'en garde que des raccourcis sur la position de la partie (`CoupsLegaux()`, `CampAuTraitEnEchec()`, `RetourneChaineFenActuel()`…) et `ExecutionCoup`, qui joue par `Regles.Jouer` puis redessine les cases changées et lance les événements. Toute nouvelle règle va dans `Regles`, avec une `Position` en paramètre. Étape 2 (2026-10-23) : plus aucun calcul de l'application ne remplace la position de la partie (`CalculerSur` supprimé) ; vérifié en comparant l'ancien et le nouveau code sur les 381 parties de `BrunoAllGames.pgn` (FEN, notations, coups légaux, variantes converties et relues : sorties identiques, deux fois plus rapide).
- `LogiqueMouvements` notifie l'UI via des événements statiques (`DessinePiece`, `DessineSymbole`, `AfficheCoupBlanc/Noir`, etc.) abonnés dans `EchiquierPrincipal.BrunoInterfaceGraphique_Load`.
- Les événements statiques sont invoqués avec `?.Invoke(...)` : la logique fonctionne sans interface abonnée (tests). Garder cette forme pour tout nouvel appel d'événement.
- `LogiqueMouvements.cs` n'a aucun `using` Windows Forms ni Krypton : la logique ne doit jamais afficher de fenêtre ni de message (utiliser un événement, une valeur de retour ou `Debug.WriteLine`).
- `EchiquierPrincipal._cheminMoteur` est toujours le chemin complet du moteur en cours, `_nomMoteurChoisi` son nom affiché. L'application ne change jamais son dossier courant (`MoteurUci.Start` fixe le dossier de travail du moteur).
- `MoteurUci` n'a aucun membre statique : l'objet `EchiquierPrincipal.MoteurUci` (gardé quand on change de moteur) est passé aux fenêtres de réglage (`ParametresDeBase`, `ParametresUciStockfish`). Il lance le moteur comme `Process` avec stdin/stdout redirigés. `ProcOutputDataReceived` s'exécute sur un **thread non-UI** : il décode chaque ligne une seule fois avec `LigneUci.Analyser` (résultat dans `MoteurUci.DerniereLigne`), puis déclenche `AfficheUci`, `AfficheDonneesBrutes`, `AfficheCoupMoteur` ; les gestionnaires côté formulaire passent par `SurLeThreadInterface(action)` (Invoke protégé : ignoré si la fenêtre est fermée ou en cours de destruction ; un `Invoke` nu sur la fenêtre détruite arrêtait l'application à la fermeture) et lisent `DerniereLigne` plutôt que redécouper le texte. `MoteurUci.Quitte` met `Proc` à null dès l'envoi de `quit` (`Interlocked.Exchange`) : les dernières lignes du moteur sont ignorées (`sender != Proc`). **Moteur arrêté tout seul** (2026-10-27 : un moteur qui plantait laissait la partie figée sans rien dire) : `Proc.Exited` → `MoteurUci.ProcExited`, qui oublie le processus s'il est toujours celui en cours (`Interlocked.CompareExchange` : jamais après `Quitte`, `Demarre` devient faux, demandes remises à zéro) et lance `MoteurArrete(moteur, code de sortie)` (thread non-UI, testé avec whoami.exe et cmd.exe) ; `EchiquierPrincipal.MoteurArreteSansDemande` le note dans le journal, relance d'office l'analyste (message seulement s'il analysait, analyse interrompue) et, pour le moteur qui joue, abandonne sa réflexion puis propose de le relancer (il rejoue si c'est à lui) ; ignoré pendant l'installation d'une mise à jour de Stockfish (`_miseAJourStockfish`, arrêts voulus). Les scores UCI sont du point de vue du camp au trait (mat négatif = le camp au trait est maté) ; ils sont convertis une fois pour toutes du point de vue des Blancs (camp au trait de `PositionDesVariantes`) par `AnalyseMoteur.cs` : tout ce qui est affiché suit la convention + = avantage blanc (« M3 » = les Blancs matent en 3).

**Evaluations et variantes** (`AnalyseMoteur.cs`, sans Windows Forms, testé) : `Evaluation` (centipions ou mat, du point de vue des Blancs ; `Texte`, `Symbole`, `Appreciation` en 7 niveaux : = sous 0.30, ⩲/⩱ léger avantage jusqu'à 0.70, ±/∓ avantage jusqu'à 2.00, +-/-+ gain, seuils `SeuilLegerAvantage`/`SeuilAvantage`/`SeuilGain`, `TexteMat`), `LigneAnalyse` (numéro de variante, évaluation, `VariantePgn` limitée à `SuiviAnalyse.CoupsAffiches` coups **entiers**, `Debut`) et `SuiviAnalyse` (`_pilote.Lignes`, remis à zéro à chaque demande au moteur) qui garde la dernière ligne de **chaque** variante : une ligne sans score garde le score de sa propre variante. `AfficheInfoMoteur` ne fait qu'afficher ce que renvoie `_pilote.Lignes.Ajouter(ligne, PositionDesVariantes)`, et la fin d'analyse lit `_pilote.Lignes.Meilleure` : ne jamais relire un résultat dans le texte affiché d'un contrôle. Pendant l'analyse d'une position (`AnalysePosition_Click`), la fenêtre de suivi de l'analyse de partie sert aussi (2026-10-17 : on ne savait pas ce qui se passait) : `OuvreFenetreSuivi(titre, bouton, arrêt)`, « Analyse de la position », position (`NomDeLaPosition`), score et meilleure suite en direct (`AfficheInfoMoteur`), barre et temps restant (`Timer_Tick` → `FenetreAnalyse.MontreProgression`) ; son bouton « Arrêter » envoie `stop` au moteur, dont la réponse (`bestmove`, demande non périmée) donne le résultat comme à la fin du temps ; fermée à la fin (avant la boîte de message) et par `AbandonneReflexion`. Fin de l'analyse d'une position : boîte de message du résultat (voulu ainsi ; un essai de fenêtre placée sous l'échiquier a été annulé à sa demande), résultat aussi sous l'échiquier (1re ligne de variante centrée en gras « Meilleure suite (+0.35, …) : … », barre d'état) avec une flèche verte du coup conseillé, effacée par `AbandonneReflexion` (toute action qui change la position). Les réponses `bestmove (none)` / `0000` (aucun coup légal) sont traitées par l'interface dans `AfficheUci` : `LogiqueMouvements.CampAuTraitEnEchec()` distingue mat et pat. Le thread du moteur ne modifie jamais l'état de la partie.
- **Numérotation des demandes** (`SuiviDemandesMoteur.cs`, `MoteurUci.Demandes`) : chaque `go` reçoit un numéro, et le n-ième `bestmove` répond au n-ième `go` (garantie UCI). `MoteurUci.AbandonneDemandeEnCours()` envoie `stop` et rend la demande périmée : ses lignes `info` et son `bestmove` sont ignorés (`MoteurUci.LigneAbandonnee`, vérifié dans `AfficheUci` et `AfficheCoupMoteur` sur le thread de l'interface). `JeuMoteurUci` abandonne d'office la demande précédente. Côté interface, **toute action qui change la partie ou la position appelle `AbandonneReflexion()` en premier** (retour arrière, résultat, nouvelle partie, chargement, parcours, analyse, changement de moteur, coup de l'humain) : c'est ce qui permet de laisser les boutons actifs pendant la réflexion. Les lignes d'un ancien processus moteur sont ignorées (`sender != Proc`). Le nombre de variantes est centralisé dans `MoteurUci.NombreLignesPV` (initialisé depuis le `.ini`, modifié via `DefinitMultiPV`) : ne pas envoyer `MultiPV` en dur.
- Fenêtre du protocole (`DonneesBrutesUci.AjouteLigne`) : seules les 2 000 dernières lignes sont gardées (retaille par paquets de 500), et `EchiquierPrincipal.AfficheDonneesBrutes` prend le texte de la ligne tout de suite puis l'affiche par `BeginInvoke` (sans bloquer la lecture du moteur) : ne jamais relire `MoteurUci.DataUci` plus tard, la ligne suivante l'aura remplacé.
- **Joueurs affichés** : les noms et Elo des étiquettes et de l'en-tête PGN (`PartieEnCours.White/Black/WhiteElo/BlackElo`) ne s'écrivent que par `EchiquierPrincipal.AfficheJoueurs` (toujours ensemble ; une seule étiquette par camp, `LabelJoueurBlanc`/`LabelJoueurNoir`, au texte « [Elo] Nom » via `TexteJoueur`, « [?] Nom » si l'Elo est vide, rien sans nom ; ce sont des `EtiquetteUneLigne`, comme les pendules : un `Label` qui ne va jamais à la ligne, centré en hauteur, terminé par « … » si le texte est trop long ; les pendules ont `ReduitPourTenir` : leur police rétrécit jusqu'à ce que le temps tienne, ex : « 1:30:00 »). `AfficheJoueursDeLaPartie()` les déduit de `_partie.Blancs/Noirs` (`_nomHumain`/`_joueurElo` ou `_nomMoteur`/`_moteurElo`) : nouvelles parties, « Reprendre ici ». Après un chargement FEN, les noms sont vides (ce n'est la position ni de l'humain ni du moteur). `AfficheMoteurDansLaPartie` n'agit que si les noms affichés viennent de `AfficheJoueursDeLaPartie` (`_nomsHumainMoteur`) : après une FEN, une partie PGN, un en-tête saisi ou « humain contre humain », un changement de moteur ne touche pas aux noms. `AfficheMoteurDansLaPartie()` ne change que le ou les camps joués par le moteur (jamais un joueur humain ni une partie PGN chargée) : nom provisoire (nom du fichier) au changement de moteur, puis nom annoncé (`id name`), et Elo (`DefinitEloMoteur`, appelé par `ParametresDeBase`). La partie PGN chargée et la fenêtre « Entête PGN » passent leurs propres valeurs à `AfficheJoueurs`. Le temps de réflexion minimum est 1 s (`go movetime 0` ferait réfléchir Stockfish sans fin) : `LimiteTemps.Duree` l'impose.
- Réinitialiser une partie passe par `Outils.MiseaZeroListes()` ; l'en-tête PGN d'une nouvelle partie (nouvelle partie, FEN, saisie de position) par `EnteteNouvellePartie()` (date du jour, ECO vidé : rien ne reste d'une partie PGN chargée). PlyCount = `LogiqueMouvements.DemiCoupsJoues` (jamais `ListeCoupsFen.Count`, qui compte l'élément « position de départ »).
- **Erreurs venues du thread du moteur** : `SurLeThreadInterface` exécute l'action dans un `try` sur le thread de l'interface (`Program.ErreurImprevue` : journal + message, l'application continue) ; renvoyée par `Invoke` sur le thread du moteur, l'erreur arrêtait l'application. `MoteurUci.ProcOutputDataReceived` note toute erreur de décodage dans le journal (`TraiteLigneDuMoteur`). Le moteur se lance par `EchiquierPrincipal.LanceMoteur` (fichier absent : journal + message, `MoteurUci.Proc` reste null), y compris au démarrage, où les menus sont réactivés dans tous les cas.
- **Pièce prise en main** (1er clic, `_clickCaseSource` à false, pièce au curseur) : `AnnuleSelectionPiece()` la remet sur sa case ; appelée par `AbandonneReflexion` (donc avant toute action qui change la partie) et au début du parcours. Le clic d'arrivée remet `_clickCaseSource` à true avant `AbandonneReflexion`.

**Calculs « pour voir »** (légalité, échec, mat, variantes du moteur `Outils.VarianteUciVersPgn`, analyse de partie, variantes du PGN, rejeu de la meilleure suite) : appeler `Regles` sur une **copie** (`position.Copier()`, ou `PositionDepuisFen(fen)` qui en crée une), jamais sur `PositionActuelle`. Pour jouer une suite de coups UCI sur la copie : `ChargementPartie.JoueCoupUci(copie, uci)` (= `Regles.Jouer`, avec la promotion) ; `Regles.SimuleCoup` ne déplace que les pièces (tour du roque et pion pris en passant compris). Rien ne se redessine : seul `ExecutionCoup` (la partie) lance les événements d'affichage. `LogiqueMouvements.CalculerSurCopie` (qui remplace un instant la position de la partie par une copie) ne sert plus qu'aux tests (perft joués par `ExecutionCoup`).

**Position affichée ≠ position de la partie** : l'échiquier montre soit la partie (`PositionActuelle`), soit une position passée pendant le parcours (`EchiquierPrincipal._positionAffichee`, index `_indexAffiche` dans `ListeCoups`, -1 = position initiale). `AfficheCoupDeLaPartie(index)` (utilisé par Préc/Suiv/Début/Fin et par un clic sur la feuille de partie) lit la FEN avec `LogiqueMouvements.PositionDepuisFen` et la dessine sans toucher à la partie ; `RetourPositionCourante()` revient à la partie (bouton ou touche Fin, clic sur le dernier coup de la feuille ; plus par un clic sur l'échiquier : il y ramenait souvent sans le vouloir). Retour arrière est grisé pendant le parcours (il annulerait un coup autre que celui affiché). Pendant le parcours, l'échiquier est inactif (`MetAJourPlateau`).

**Classe `Partie`** (`Partie.cs`, sans Windows Forms, testée) : `EchiquierPrincipal._partie` (exposée par `PartieCourante`) porte le mode de la partie (`ModePartie` : `AucunePartie`, `EnCours`, `Terminee`, `LectureSeule`), qui joue chaque camp (`Blancs`/`Noirs` : `Joueur.Humain` ou `Joueur.Moteur` ; `EntreHumains`, `JoueurAuTrait`, `MoteurAuTrait`, `HumainAuTrait`), `DepuisPosition` (départ FEN) et `RejeuPgn`. Ses actions : `Commencer(blancs, noirs)`, `CommencerDepuisPosition()` (l'humain joue le camp au trait), `Terminer()`, `Reprendre()`, `PasserEnLectureSeule()`, `MoteurPrendLeTrait()` (« Ordinateur joue »), `AnnulerDernierCoup()` (retour arrière : position rétablie depuis la FEN, reprise d'une partie terminée) et `ReprendreDepuis(index)` (bouton « Reprendre ici » du groupe de parcours, actif pendant le parcours et sur une partie PGN en lecture seule, y compris à sa position finale où rien n'est supprimé ; refusé sur un mat ou un pat : supprime les coups après la position affichée ; une partie terminée reprend, une partie PGN en lecture seule devient jouable avec l'humain au camp au trait ; le formulaire, `BoutonReprendreIci_Click`, efface le résultat, fixe les en-têtes et fait jouer le moteur si c'est son tour). Après un coup de l'humain, le moteur n'est sollicité que si `MoteurAuTrait` (donc jamais après un mat, un pat ou une nulle). Il n'existe plus de `_humain`, `_couleurHumain` ni `OrdinateurJoueBlanc/Noir` : tout passe par `_partie`.

**État de la partie et commandes actives** : `_partie.Mode` est le seul état de partie ; `MetAJourCommandes()` calcule **en un seul endroit** l'état de Retour arrière, Préc/Suiv/Début/Fin (et flèches du clavier), Analyse, Gain/Nulle, Ordinateur joue, Entête PGN, Saisie partie et du plateau (`MetAJourPlateau`, qui combine le mode, le parcours et `_plateauAutorise` = « c'est au joueur de bouger », fixé par `PlateauEnable`). Ne jamais écrire le `.Enabled` de ces commandes ailleurs : changer l'état puis appeler `MetAJourCommandes()`. Le mode change dans `CommencerPartie` (toutes les nouvelles parties → `EnCours`), `ChargementPartie.ChargerPosition` (`EnCours`), `ChargementPartie.ChargerPartiePgn` (`LectureSeule` à la fin), `GestionResultat` (`Terminee`, point de passage de toutes les fins : mat, pat, nulles, abandon) et `RetourArriere_Click` : un retour arrière sur une partie terminée la remet `EnCours` (`Partie.AnnulerDernierCoup`) et efface le résultat affiché (`EffaceResultat`). Pendant le parcours, les dessins demandés par la partie (coup du moteur) sont ignorés (`DessinePieceDeLaPartie`) et la partie continue normalement. `MiseenplaceFen` ne sert qu'aux actions qui **changent** la partie (retour arrière, chargement FEN) ; ces actions et les nouvelles parties appellent `QuitteParcours()` d'abord. - **Journal des erreurs** (`Journal.cs`, sans Windows Forms, testé) : `BrunoGUI.log` à côté de l'exécutable (`Journal.Chemin`), `Journal.Erreur(contexte, exception)` (type, message, pile d'appels) et `Journal.Info(message)` ; ne lève jamais d'exception ; au-delà de 1 Mo, renommé en `.log.old`. `Program.Main` branche les gestionnaires globaux : une exception imprévue sur le thread de l'interface est notée puis expliquée par un message (l'application continue, `ErreurImprevue`) ; ailleurs (thread du moteur, tâches) elle est notée. Tout `catch` qui avale une erreur doit l'écrire dans le journal (pas seulement `Debug.WriteLine`) ; un `catch (Exception)` général n'est admis que si les causes sont trop variées pour être listées (réseau, fichier choisi par l'utilisateur), avec un commentaire qui le dit.
- **Saisie d'une position** (bouton « Saisie position », sous « Saisie partie » ; grisé pendant une analyse de partie, `MetAJourCommandes`) : fenêtre `SaisiePosition.cs` (KryptonForm construite en code : échiquier dessiné avec les images et couleurs de `_vue`, palette de 12 pièces, clic gauche pose (ou retire la même pièce), clic droit vide : pas de gomme, elle faisait double emploi ; les messages sont à droite sous la palette ; trait, 4 roques, case en passant, numéro du coup, boutons « Copier FEN » et « Coller une FEN » ; la FEN, OK et Annuler sur une seule ligne sous l'échiquier, messages sur deux lignes au plus à droite sous la palette ; OK refusé tant que `ChargementPartie.ErreurFen` donne une raison). La logique est dans `EditeurPosition.cs` (sans Windows Forms, testé) : un objet `Position`, `Poser` (un seul roi par camp), roques possibles seulement roi et tour en place (accordés d'office quand ils le deviennent, jamais rétablis s'ils ont été décochés), cases en passant possibles (`CasesEnPassantPossibles`), `Fen` par `RetourneChaineFenActuel` sur la copie. Départ : la position affichée ; après OK, `ChargeFenDansLaPartie` (commun avec « Charger position FEN ») en fait une nouvelle partie, l'humain au trait.
- `Bibliotheque.cs` : une bibliothèque introuvable lève une exception claire au chargement (`PolyglotBibliothequeLecture`, la précédente reste active) et `TrouverLesEntrees` ne renvoie alors aucun coup (`PolyglotBibliotheque.Disponible`) ; `EchiquierPrincipal.RecupereBibliotheque` affiche un message au lieu de planter.
- Fenêtre « Partie PGN » (`AffichePgn`) : 7 boutons de 100 px (PGN Intl., **PGN commenté** = `RetourneContenuPgn(…, pourFichier: true)`, la partie telle qu'elle serait enregistrée, PGN Fr., algébrique, UCI, FEN, Fermer). Icônes des options de menu ajoutées par le code (2026-10-18) : `Pendule` pour « Durées de l'analyse de partie », `Stockfish` pour la mise à jour, l'icône de l'application pour « A propos », et des drapeaux dessinés (`EchiquierPrincipal.Drapeau` : Windows n'affiche pas les drapeaux en emoji) pour Options > Langue.
- Fenêtres secondaires : la liste des parties PGN (`FichierPartiePgn`), comme les autres, est masquée par la croix rouge et jamais détruite ; le texte du bouton « Affiche/Masque liste parties » suit sa visibilité. Les nouvelles parties (menus, dialogue Stockfish) et l'ouverture d'un fichier PGN ne changent rien avant la confirmation : « Annuler » laisse la partie et la réflexion du moteur intactes.
- `MiseAJourStockfish.cs` : deux étapes. `RechercherNouvelleVersion` compare `sf_<n>` (tiré de `id name Stockfish <n>`) au tag de la dernière release GitHub et renvoie la version (tag, lien, taille) ou `null` si à jour, sans rien arrêter ni télécharger. `Installer` télécharge le zip Windows adapté (`ChoisirArchive`, testé : depuis Stockfish 19, un seul binaire « universal » par processeur, `x86-64` ou `arm64` selon `RuntimeInformation.OSArchitecture`) et remplace le `stockfish.exe` **du dossier de sortie** (arrêt des seuls processus lancés depuis ce fichier, après le téléchargement ; sauvegarde `.old` restaurée si la nouvelle version ne répond pas `uciok` ; quelques nouvelles tentatives si le fichier est verrouillé, ex : par OneDrive). Le moteur doit ensuite être redémarré. Attention : une recompilation complète (Rebuild, `--no-incremental`) nettoie le dossier de sortie et y recopie le `stockfish\stockfish.exe` du dépôt (version plus ancienne) : il faut alors refaire la mise à jour. Au démarrage (`EchiquierPrincipal.VerificationAutomatiqueMiseAJour`, avant `MoteurUci.Start`), la recherche n'a lieu que tous les `VerificationMiseAJourJours` jours (`BrunoGUI.ini`, 30 par défaut, 0 = jamais ; date `DerniereVerificationMiseAJour` dans les préférences) ; au démarrage comme par le bouton, l'installation n'a lieu qu'après accord de l'utilisateur (`DemandeInstallation`). Une exception signale une vraie erreur (ex : hors ligne). Le `.csproj` copie `stockfish\stockfish.exe` en `PreserveNewest` pour ne pas écraser une version mise à jour à chaque compilation.

## Chemins et fichiers d'exécution

- `Chemins.RepertoireRacine` = `Application.StartupPath` (déploiement portable) : moteurs, livres et `.ini` sont cherchés **à côté de l'exécutable**, pas à la racine du dépôt. Un fichier ajouté dans `Moteurs_UCI\` ou `BibliothèquesPolyglot\` doit donc être déclaré dans le `.csproj` avec `CopyToOutputDirectory` (seuls Rodent IV, Sargon et `stockfish\stockfish.exe` le sont côté moteurs).
- `BrunoGUI.ini` (format `clé = valeur`, `;` pour les commentaires) est lu par `Parametres.ChargerDepuisIni`. Seules les clés présentes dans le `switch` sont lues ; une nouvelle clé doit y être ajoutée. Les couleurs acceptent un nom .NET (`Peru`) ou un code `#RRGGBB` (`Parametres.ConvertitCouleur`), avec le style Lichess par défaut. `NombreCoeursThread` et `TableHachage` sont envoyés au moteur à la réception de `uciok` (`MoteurUci.EnvoieOptionsDemarrage`), une seule fois, seulement si le moteur déclare ces options et **seulement à Stockfish** (`MoteurUci.NomAnnonce`) : avec plusieurs threads, Rodent IV ignore MultiPV. **Deux fichiers** : `BrunoGUI.ini` contient les valeurs par défaut, livrées avec l'application et **jamais écrites** par elle (copié en `Always` : on peut le modifier librement dans le dépôt). `BrunoGUI.preferences.ini`, créé à côté de l'exécutable (hors dépôt), contient les préférences personnelles : `Parametres.Charger(dossier)` lit le premier puis le second par-dessus. À la fermeture, `EchiquierPrincipal.SauvePreferences` y enregistre les réglages de l'interface (couleurs, nom, temps de réflexion, choix de « Nouvelle partie », MultiPV, Threads, Hash, bibliothèque) via `Parametres.SauverPreferences`, qui remplace les valeurs sur place en conservant commentaires, ordre et clés inconnues. Le moteur, son site, l'Elo de l'humain et la palette restent uniquement dans `BrunoGUI.ini`. La clé `Palette` (nom d'un `Krypton.Toolkit.PaletteMode`, ex : `Microsoft365Silver`, `Office2013White`) choisit la palette de toute l'application (`Program.ConfigureKrypton`, qui met aussi les boutons des boîtes de message en français) ; absente : `Microsoft365Blue`, la palette par défaut de Krypton 95. Les réglages Threads/Hash passent par `MoteurUci.DefinitThreads`/`DefinitHachage` (mémorisés et renvoyés à chaque redémarrage du moteur, par exemple à chaque « Nouvelle partie »).
- `BrunoGUI.ini`, `Bruno_NB.jpg`, `Langues\` et `Aide\` sont cherchés via `Chemins.RepertoireRacine` : ne jamais utiliser de chemin relatif au dossier courant (l'application est parfois lancée depuis un raccourci).
- Le dossier `Tests\` est exclu de la compilation de l'application dans `BrunoGUI_GenII.csproj` (le projet racine inclut sinon tous les `.cs` des sous-dossiers).
- `stockfish\src\` et `stockfish\wiki\` sont les sources/doc upstream de Stockfish, fournies pour référence — elles ne font pas partie du build C#.
