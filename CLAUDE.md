# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Projet

BrunoGUI_GenII : interface graphique d'échecs Windows (C# WinForms, .NET 8, `net8.0-windows`) qui pilote des moteurs UCI (Stockfish par défaut, plus Rodent IV, Sargon 1978, etc.). Licence GPL-3.0-or-later. Tout le code, les identifiants et les commentaires sont en français — garder cette convention.

## Commandes

```bash
dotnet build BrunoGUI_GenII.sln
```

```bash
dotnet run --project BrunoGUI_GenII.csproj
```

Tests de la logique d'échecs (projet console sans framework externe, `Tests/Program.cs`) :

```bash
dotnet run --project Tests
```

```bash
dotnet run --project Tests -- --complet
```

- Les tests couvrent les règles (roque, prise en passant, promotion, 50 coups, lecture FEN, conversion de variantes UCI), la notation PGN des coups ambigus (avec aller-retour écriture/relecture), la liste des coups (alignement, départ FEN, retour arrière, « # » du mat), le décodage des lignes UCI (`LigneUci`), la classe `Position` (copie, `CalculerSurCopie`), la classe `Partie` (qui est au trait, retour arrière, reprise après un mat, départ FEN, lecture seule, « Reprendre ici »), la classe `PiloteMoteur` avec un faux moteur `FauxMoteur` (bibliothèque puis moteur, analyse, abandon, coup UCI avec promotion), les évaluations et variantes du moteur (`Evaluation`, `SuiviAnalyse` : point de vue des Blancs, mat, score par variante, limite en coups entiers, promotion) et des **perft** (chaque coup y est joué via `CalculerSurCopie`) comparés aux valeurs de référence (position initiale, Kiwipete, positions 3 à 5). `--complet` ajoute les perft profonds (~15 s). Toute modification du générateur de coups doit garder les perft verts.
- Pour ajouter un test : appeler `Charger(fen)`, jouer avec `L.ExecutionCoup(source, destination)`, puis `Verifie(nom, condition, détail)`.
- L'interface graphique n'a pas de tests : vérifier à la main dans l'application tout ce qui touche à `EchiquierPrincipal` ou au moteur.
- La solution compile sans avertissement : garder cet état.
- `CA1416` est désactivé dans le `.csproj`.
- `git` n'est pas dans le PATH de PowerShell sur cette machine : utiliser celui de Visual Studio 2022 (`C:\Program Files\Microsoft Visual Studio\2022\Community\Common7\IDE\CommonExtensions\Microsoft\TeamFoundation\Team Explorer\Git\cmd\git.exe`).
- GitHub Actions (`.github/workflows/tests.yml`) compile et lance les tests à chaque push. La compilation y passe `-p:SignManifests=false` : le certificat ClickOnce n'existe que sur le PC de développement.
- `.gitattributes` impose CRLF aux fichiers du projet (`.cs`, `.csproj`, `.sln`, `.resx`, `.md`, `.ini`, `.yml`) : écrire les nouveaux fichiers en CRLF.

## Architecture

**Point d'entrée** : `Program.cs` affiche le splash (`EcranDemarrage`), puis lance `EchiquierPrincipal` (palette par défaut de Krypton 95, pas de `KryptonManager`).

**`EchiquierPrincipal`** (~130 Ko) est le formulaire central : il gère l'échiquier, les menus, la feuille de partie, l'analyse et l'orchestration du moteur. Les autres formulaires (`ParametresDeBase`, `ParametresUciStockfish`, `PartieForceModule`, `FenetrePartie`, `AffichePgn`, `FichierPartiePgn`, `DonneesBrutesUci`, `FenetreAide`) sont des boîtes de dialogue secondaires.

**Classe `Position` + façade statique + événements statiques** — c'est le modèle clé à comprendre :
- `Position` (`Position.cs`) regroupe tout l'état d'une position : plateau 120 cases, trait, 4 droits de roque, case en passant, compteur des 50 coups, numéro de coup, `Echec`/`EchecetMat`. `Copier()` en fait une copie indépendante.
- `LogiqueMouvements.PositionActuelle` est la position de la partie. Les propriétés statiques historiques (`PiecesEchiquier`, `QuiJoue`, `PetitRoqueBlancPossible`…, `IndexCaseEnPassant`, `SansPrise`, `NombreCoupsJoues`, `Echec`, `EchecetMat`) ne sont que des raccourcis vers cet objet : le reste du code les utilise sans connaître `Position`. Tout nouvel élément d'état de la position doit être ajouté à `Position` (sinon il ne serait ni copié ni restauré).
- Restent hors de `Position` (état de partie ou de coup, non copié) : la liste des coups (`ListeCoups`), `PartieEnCoursMat/Pat`, `PromotionPiece`, `CoupValide`.
- `LogiqueMouvements` notifie l'UI via des événements statiques (`DessinePiece`, `DessineSymbole`, `AfficheCoupBlanc/Noir`, etc.) abonnés dans `EchiquierPrincipal.BrunoInterfaceGraphique_Load`.
- Les événements statiques sont invoqués avec `?.Invoke(...)` : la logique fonctionne sans interface abonnée (tests). Garder cette forme pour tout nouvel appel d'événement.
- `LogiqueMouvements.cs` n'a aucun `using` Windows Forms ni Krypton : la logique ne doit jamais afficher de fenêtre ni de message (utiliser un événement, une valeur de retour ou `Debug.WriteLine`).
- `EchiquierPrincipal._cheminMoteur` est toujours le chemin complet du moteur en cours, `_nomMoteurChoisi` son nom affiché. L'application ne change jamais son dossier courant (`MoteurUci.Start` fixe le dossier de travail du moteur).
- `MoteurUci` lance le moteur comme `Process` avec stdin/stdout redirigés. `ProcOutputDataReceived` s'exécute sur un **thread non-UI** : il décode chaque ligne une seule fois avec `LigneUci.Analyser` (résultat dans `MoteurUci.DerniereLigne`), puis déclenche `AfficheUci`, `AfficheDonneesBrutes`, `AfficheCoupMoteur` ; les gestionnaires côté formulaire doivent passer par `InvokeRequired`/`Invoke` et lire `DerniereLigne` plutôt que redécouper le texte. Les scores UCI sont du point de vue du camp au trait (mat négatif = le camp au trait est maté) ; ils sont convertis une fois pour toutes du point de vue des Blancs (camp au trait de `PositionDesVariantes`) par `AnalyseMoteur.cs` : tout ce qui est affiché suit la convention + = avantage blanc (« M3 » = les Blancs matent en 3).

**Evaluations et variantes** (`AnalyseMoteur.cs`, sans Windows Forms, testé) : `Evaluation` (centipions ou mat, du point de vue des Blancs ; `Texte`, `Symbole`, `Appreciation`, `TexteMat`), `LigneAnalyse` (numéro de variante, évaluation, `VariantePgn` limitée à `SuiviAnalyse.CoupsAffiches` coups **entiers**, `Debut`) et `SuiviAnalyse` (`_pilote.Lignes`, remis à zéro à chaque demande au moteur) qui garde la dernière ligne de **chaque** variante : une ligne sans score garde le score de sa propre variante. `AfficheInfoMoteur` ne fait qu'afficher ce que renvoie `_pilote.Lignes.Ajouter(ligne, PositionDesVariantes)`, et la fin d'analyse lit `_pilote.Lignes.Meilleure` : ne jamais relire un résultat dans le texte affiché d'un contrôle. Les réponses `bestmove (none)` / `0000` (aucun coup légal) sont traitées par l'interface dans `AfficheUci` : `LogiqueMouvements.CampAuTraitEnEchec()` distingue mat et pat. Le thread du moteur ne modifie jamais l'état de la partie.
- **Numérotation des demandes** (`SuiviDemandesMoteur.cs`, `MoteurUci.Demandes`) : chaque `go` reçoit un numéro, et le n-ième `bestmove` répond au n-ième `go` (garantie UCI). `MoteurUci.AbandonneDemandeEnCours()` envoie `stop` et rend la demande périmée : ses lignes `info` et son `bestmove` sont ignorés (`MoteurUci.LigneAbandonnee`, vérifié dans `AfficheUci` et `AfficheCoupMoteur` sur le thread de l'interface). `JeuMoteurUci` abandonne d'office la demande précédente. Côté interface, **toute action qui change la partie ou la position appelle `AbandonneReflexion()` en premier** (retour arrière, résultat, nouvelle partie, chargement, parcours, analyse, changement de moteur, coup de l'humain) : c'est ce qui permet de laisser les boutons actifs pendant la réflexion. Les lignes d'un ancien processus moteur sont ignorées (`sender != Proc`). Le nombre de variantes est centralisé dans `MoteurUci.NombreLignesPV` (initialisé depuis le `.ini`, modifié via `DefinitMultiPV`) : ne pas envoyer `MultiPV` en dur.
- Réinitialiser une partie passe par `Outils.MiseaZeroListes()`.

**Calculs « pour voir »** : la légalité (`TestMouvementValide`), l'échec après un coup (`CoupNotationAlgebriquePGN`, qui met à jour `Echec` de la position réelle avec le résultat), le mat (`CalculeEchecEtMat`) et les variantes du moteur (`Outils.VarianteUciVersPgn`) s'exécutent dans `LogiqueMouvements.CalculerSurCopie(() => …)`. Cette fonction remplace temporairement `PositionActuelle` par une copie, puis remet l'originale, même en cas d'exception. Dans ce cadre, jouer les coups avec `SimuleCoup` (qui gère la tour du roque et le pion pris en passant, sans affichage), jamais `DeplacementPiece` seul. Tout ce qui est hors de `Position` (listes de coups, `PromotionPiece`, événements d'affichage) n'est **pas** protégé par la copie. Un calcul sur copie ne déclenche aucun redessin, contrairement à `MiseenplaceFen`.

**Position affichée ≠ position de la partie** : l'échiquier montre soit la partie (`PositionActuelle`), soit une position passée pendant le parcours (`EchiquierPrincipal._positionAffichee`, index `_indexAffiche` dans `ListeCoups`, -1 = position initiale). `AfficheCoupDeLaPartie(index)` (utilisé par Préc/Suiv/Début/Fin et par `FenetrePartie`) lit la FEN avec `LogiqueMouvements.PositionDepuisFen` et la dessine sans toucher à la partie ; `RetourPositionCourante()` revient à la partie (bouton Fin, clic sur l'échiquier, fermeture de la Liste des coups). Retour arrière est grisé pendant le parcours (il annulerait un coup autre que celui affiché). Pendant le parcours, les cases restent cliquables (sauf partie en lecture seule), même quand ce n'est pas au joueur de jouer, pour que le clic ramène à la partie.

**Classe `Partie`** (`Partie.cs`, sans Windows Forms, testée) : `EchiquierPrincipal._partie` (exposée par `PartieCourante`) porte le mode de la partie (`ModePartie` : `AucunePartie`, `EnCours`, `Terminee`, `LectureSeule`), qui joue chaque camp (`Blancs`/`Noirs` : `Joueur.Humain` ou `Joueur.Moteur` ; `EntreHumains`, `JoueurAuTrait`, `MoteurAuTrait`, `HumainAuTrait`), `DepuisPosition` (départ FEN) et `RejeuPgn`. Ses actions : `Commencer(blancs, noirs)`, `CommencerDepuisPosition()` (l'humain joue le camp au trait), `Terminer()`, `Reprendre()`, `PasserEnLectureSeule()`, `MoteurPrendLeTrait()` (« Ordinateur joue »), `AnnulerDernierCoup()` (retour arrière : position rétablie depuis la FEN, reprise d'une partie terminée) et `ReprendreDepuis(index)` (bouton « Reprendre ici » du groupe de parcours, actif seulement pendant le parcours : supprime les coups après la position affichée ; une partie terminée reprend, une partie PGN en lecture seule devient jouable avec l'humain au camp au trait ; le formulaire, `BoutonReprendreIci_Click`, efface le résultat, fixe les en-têtes et fait jouer le moteur si c'est son tour). Après un coup de l'humain, le moteur n'est sollicité que si `MoteurAuTrait` (donc jamais après un mat, un pat ou une nulle). Il n'existe plus de `_humain`, `_couleurHumain` ni `OrdinateurJoueBlanc/Noir` : tout passe par `_partie`.

**État de la partie et commandes actives** : `_partie.Mode` est le seul état de partie ; `MetAJourCommandes()` calcule **en un seul endroit** l'état de Retour arrière, Préc/Suiv/Début/Fin (et flèches du clavier), Liste des coups, Analyse, Gain/Nulle, Ordinateur joue, Entête PGN, Saisie partie et du plateau (`MetAJourPlateau`, qui combine le mode, le parcours et `_plateauAutorise` = « c'est au joueur de bouger », fixé par `PlateauEnable`). Ne jamais écrire le `.Enabled` de ces commandes ailleurs : changer l'état puis appeler `MetAJourCommandes()`. Le mode change dans `CommencerPartie` (toutes les nouvelles parties → `EnCours`), `ChargePositionFen` (`EnCours`), `ParcoursPartie` (`LectureSeule` à la fin), `GestionResultat` (`Terminee`, point de passage de toutes les fins : mat, pat, nulles, abandon) et `RetourArriere_Click` : un retour arrière sur une partie terminée la remet `EnCours` (`Partie.AnnulerDernierCoup`) et efface le résultat affiché (`EffaceResultat`). Pendant le parcours, les dessins demandés par la partie (coup du moteur) sont ignorés (`DessinePieceDeLaPartie`) et la partie continue normalement. `MiseenplaceFen` ne sert qu'aux actions qui **changent** la partie (retour arrière, chargement FEN) ; ces actions et les nouvelles parties appellent `QuitteParcours()` d'abord. L'analyse porte sur la position affichée (`_pilote.PositionAnalysee`) : ses variantes sont converties et numérotées sur cette position (`Outils.VarianteUciVersPgn(..., position)`, `LogiqueMouvements.DemiCoupAvant`, `EchiquierPrincipal.PositionDesVariantes`). Une partie PGN chargée est en lecture seule (`ModePartie.LectureSeule`) : sa position de partie est la position finale, et l'affichage démarre au début.

**Pilotage du moteur** (`PiloteMoteur.cs`, sans Windows Forms, testé avec un faux moteur) : `EchiquierPrincipal._pilote` mémorise ce qui est demandé au moteur (`Demande` : `TypeDemande.Aucune`, `CoupDePartie` ou `Analyse`, avec `PositionAnalysee`) et ne voit le moteur qu'à travers l'interface `IMoteur` (implémentée par `MoteurUci`). `DemanderCoup(fen, durée)` essaie d'abord la bibliothèque (`ChoixBibliotheque`, fixé dans le constructeur du formulaire ; un coup de bibliothèque illégal laisse la main au moteur), `DemanderAnalyse(position, durée)` analyse une copie de la position, `Abandonner()` (appelé par `AbandonneReflexion`) renvoie `true` si le moteur réfléchissait, et `ReponseRecue()` (dans `AfficheCoupMoteur`, et pour `bestmove (none)`) dit à quelle demande répond un bestmove valable : un bestmove sans demande en cours est ignoré. `PiloteMoteur.JouerCoupUci("e7e8q")` joue un coup UCI, promotion comprise (coups du moteur et de la bibliothèque). Il n'existe plus de `_analyseEnCours` ni `_positionAnalysee` dans le formulaire ; l'affichage (minuterie, textes, couleurs, message de fin d'analyse) y reste.

**Fins de partie** : mat et pat sont signalés par `ExecutionCoup` (événements `AfficheEchecEtMat`, `AfficheInfoEchec`). Les nulles automatiques passent par `LogiqueMouvements.RaisonNulle()` (triple répétition au sens FIDE avec la position initiale, 50 coups = 100 demi-coups, matériel insuffisant), appelée par l'interface après chaque coup ; elle renvoie `null` si le dernier coup a déjà maté ou pat (`DernierCoupTerminePartie`). Pendant le rejeu d'une partie PGN chargée (`Partie.RejeuPgn`), aucune nulle automatique n'est déclarée : le résultat du PGN fait foi.

**Droits de roque** : les 4 booléens `PetitRoqueBlancPossible`, `GrandRoqueBlancPossible`, `PetitRoqueNoirPossible`, `GrandRoqueNoirPossible` sont la seule source de vérité (lus/écrits dans la FEN, mis à jour dans `FaireMouvement`). `MiseenplaceFen` rétablit aussi la case en passant et le compteur des 50 coups : le retour arrière et la navigation dans la partie reposent dessus.

**Représentation de l'échiquier** : tableau « mailbox » de **120 cases** (10×12). a1 = index 21, h8 = index 98 ; les cases hors plateau valent `TypePiece.Bordure`. Les `PictureBox` de l'UI (`PictJeux`) sont indexées de la même façon. Voir le schéma en tête de `LogiqueMouvements.cs`. Dans `TypePiece`, les pièces noires ont des valeurs paires et les blanches impaires.

**Liste des coups** (`Coup.cs`) : `LogiqueMouvements.ListeCoups` est une liste d'objets `Coup` qui portent toutes les notations d'un coup (FEN de la position **après** le coup, PGN international, PGN français R/D/T/F/C, NAL, UCI ; le numéro « 12. » n'est écrit que devant les coups blancs, puis « # », « + » ou rien, puis un espace). `ListeCoupsFen`, `ListeCoupsPgnIntl`, `ListeCoupsPgnFr`, `ListeCoupsNal`, `ListeCoupsUci` sont des **vues en lecture seule** (`VueCoups`) de cette liste, toujours alignées : on ne la modifie que par `AjouteCoup`, `AjoutePositionDeDepart`, `RetireDernierCoup` (qui ne retire jamais la position de départ) et `ViderCoups`. Une partie chargée depuis un FEN commence par un élément `Coup.PositionDeDepart` (notations vides) : le code qui parcourt les coups joués doit l'ignorer (`EstPositionDeDepart`). Le « # » du mat est posé par `ExecutionCoup`, qui ne positionne toutefois `EchecetMat` qu'après les événements `AfficheCoupBlanc`/`AfficheCoupNoir` (l'interface en dépend).

**Autres modules** :
- `Bibliotheque.cs` : lecture des livres d'ouvertures Polyglot `.bin` (calcul de clé Zobrist, table Random64, lecture big-endian).
- `GestionPartiePgn.cs` / `FichierPartiePgn.cs` : génération/sauvegarde PGN (lignes ≤ 80 caractères), en-têtes (`SaisieBalises`), et parseur PGN (`ParseurPgn`, machine à états).
- `MiseAJourStockfish.cs` : deux étapes. `RechercherNouvelleVersion` compare `sf_<n>` (tiré de `id name Stockfish <n>`) au tag de la dernière release GitHub et renvoie la version (tag, lien, taille) ou `null` si à jour, sans rien arrêter ni télécharger. `Installer` télécharge le zip Windows adapté (depuis Stockfish 19, un seul binaire `x86-64-universal`) et remplace le `stockfish.exe` **du dossier de sortie** (sauvegarde `.old`, arrêt préalable des seuls processus lancés depuis ce fichier : le moteur doit ensuite être redémarré). Au démarrage (`EchiquierPrincipal.VerificationAutomatiqueMiseAJour`, avant `MoteurUci.Start`), la recherche n'a lieu que tous les `VerificationMiseAJourJours` jours (`BrunoGUI.ini`, 30 par défaut, 0 = jamais ; date `DerniereVerificationMiseAJour` dans les préférences) ; au démarrage comme par le bouton, l'installation n'a lieu qu'après accord de l'utilisateur (`DemandeInstallation`). Une exception signale une vraie erreur (ex : hors ligne). Le `.csproj` copie `stockfish\stockfish.exe` en `PreserveNewest` pour ne pas écraser une version mise à jour à chaque compilation.

## Chemins et fichiers d'exécution

- `Chemins.RepertoireRacine` = `Application.StartupPath` (déploiement portable) : moteurs, livres et `.ini` sont cherchés **à côté de l'exécutable**, pas à la racine du dépôt. Un fichier ajouté dans `Moteurs_UCI\` ou `BibliothèquesPolyglot\` doit donc être déclaré dans le `.csproj` avec `CopyToOutputDirectory` (seuls Rodent IV, Sargon et `stockfish\stockfish.exe` le sont côté moteurs).
- `BrunoGUI.ini` (format `clé = valeur`, `;` pour les commentaires) est lu par `Parametres.ChargerDepuisIni`. Seules les clés présentes dans le `switch` sont lues ; une nouvelle clé doit y être ajoutée. Les couleurs acceptent un nom .NET (`Peru`) ou un code `#RRGGBB` (`Parametres.ConvertitCouleur`), avec le style Lichess par défaut. `NombreCoeursThread` et `TableHachage` sont envoyés au moteur à la réception de `uciok` (`MoteurUci.EnvoieOptionsDemarrage`), une seule fois, seulement si le moteur déclare ces options et **seulement à Stockfish** (`MoteurUci.NomAnnonce`) : avec plusieurs threads, Rodent IV ignore MultiPV. **Deux fichiers** : `BrunoGUI.ini` contient les valeurs par défaut, livrées avec l'application et **jamais écrites** par elle (copié en `Always` : on peut le modifier librement dans le dépôt). `BrunoGUI.preferences.ini`, créé à côté de l'exécutable (hors dépôt), contient les préférences personnelles : `Parametres.Charger(dossier)` lit le premier puis le second par-dessus. À la fermeture, `EchiquierPrincipal.SauvePreferences` y enregistre les réglages de l'interface (couleurs, nom, temps de réflexion, choix de « Nouvelle partie », MultiPV, Threads, Hash, bibliothèque) via `Parametres.SauverPreferences`, qui remplace les valeurs sur place en conservant commentaires, ordre et clés inconnues. Le moteur, son site, l'Elo de l'humain et la palette restent uniquement dans `BrunoGUI.ini`. La clé `Palette` (nom d'un `Krypton.Toolkit.PaletteMode`, ex : `Microsoft365Silver`, `Office2013White`) choisit la palette de toute l'application (`Program.ConfigureKrypton`, qui met aussi les boutons des boîtes de message en français) ; absente : `Microsoft365Blue`, la palette par défaut de Krypton 95. Les réglages Threads/Hash passent par `MoteurUci.DefinitThreads`/`DefinitHachage` (mémorisés et renvoyés à chaque redémarrage du moteur, par exemple à chaque « Nouvelle partie »).
- `BrunoGUI.ini`, `Bruno_NB.jpg` et `AideBrunoGUI.rtf` sont cherchés via `Chemins.RepertoireRacine` : ne jamais utiliser de chemin relatif au dossier courant (l'application est parfois lancée depuis un raccourci).
- Le dossier `Tests\` est exclu de la compilation de l'application dans `BrunoGUI_GenII.csproj` (le projet racine inclut sinon tous les `.cs` des sous-dossiers).
- `stockfish\src\` et `stockfish\wiki\` sont les sources/doc upstream de Stockfish, fournies pour référence — elles ne font pas partie du build C#.

## UI

Composants Krypton 95 uniquement (`Krypton.Toolkit`, `Krypton.Navigator`, `Krypton.Ribbon`, `Krypton.Workspace`, espace de noms `Krypton.Toolkit`) ; l'ancienne bibliothèque `ComponentFactory.Krypton.Toolkit` a été retirée. `KryptonMessageBox.Show` prend `KryptonMessageBoxButtons` / `KryptonMessageBoxIcon` (pas les énumérations Windows Forms). Les fichiers `*.Designer.cs` sont générés par le designer WinForms : les modifier avec précaution (ou via le designer), en cohérence avec les `.resx`.
